# PS4 Auto Updater v0.2 — مرحلة ماسح الألعاب (مصدر تطويري فقط)

**هذه النسخة ليست ملف PS4 PKG ولا ELF جاهزًا للتثبيت.** بنيتُ واختبرت على Linux/PC. لا يوجد في بيئة البناء الحالية OpenOrbis SDK أو مكتبة SQLite مهيأة لهدف PS4، ولم أختبر على PS4 14.00. لا تنقل الملف التنفيذي المُنشأ على الكمبيوتر إلى PS4.

## الهدف النهائي

تطبيق PS4 يفتح ويقرأ الألعاب المثبتة تلقائيًا، ثم يعرض فقط التحديثات التي أثبت صاحب الفهرس توافقها مع نسخة اللعبة الأساسية، ثم يطلب موافقة صاحب السوني قبل أي تحميل أو تثبيت. **لا يوجد حل شامل جاهز يضمن تحديث جميع FPKG**؛ لا يمكن لأرقام CUSA وContent ID وحدها إثبات التوافق، ولا يوجد ضمن المشروع مصدر موثوق لكل تحديثات الألعاب.

## ما تغيّر عن v0.1

1. `native/scan_appdb.c`: نموذج ماسح مكتوب بلغة C99، يعتمد على قراءة `/system_data/priv/mms/app.db` باستخدام SQLite في وضع **القراءة فقط**. يستكشف الجداول `tbl_appbrowse_*`، يحدد ألعاب CUSA، ثم يحاول استكمال الإصدار وContent ID من ملفات `param.sfo` الداخلية والخارجية. يجمع الألعاب المكررة بين المستخدمين، ويستبعد الإدخالات غير المطابقة لـ CUSA والإضافات التي لا تبدو ألعابًا. **لا يغيّر قاعدة النظام ولا يثبّت أو يحمّل PKG**.
2. مخرجات `inventory.json` توضح الفرق بين `listed_in_appdb` و`metadata_available`؛ العلامة `installed_confirmed` تعني في النموذج أن **السجل موجود في قاعدة البيانات وملف البيانات موجود**، وليست إثباتًا نهائيًا أن اللعبة ستعمل.
3. `catalog/build_catalog.py`: صار يرفض عرض تحديث إذا لم يكن إدخال اللعبة مؤكّدًا في النموذج (`installed_confirmed=true`) أو إذا غابت بيانات المطابقة أو شهادة التحقق اليدوي. جميع الملفات المعتمدة تبدأ فارغة عمدًا.
4. `web/index.html`: واجهة عربية تجريبية لعرض `inventory.json` و`UPDATES.json` بعد إنشائهما، **ولا تفحص السوني مباشرة**.
5. `tests/`: اختبارات للماسح C وقائمة المطابقة. يمكن تشغيلها على الكمبيوتر دون السوني.

## تجربة على الكمبيوتر باستخدام بيانات تجريبية (لا تحتاج ملفات جهازك)

على Linux مع `cc`, `sqlite3` development headers وPython 3:

```bash
cd ps4-auto-updater-v0.2
make -C native -f Makefile.host
python3 -m unittest discover -s tests -v
```

النتيجة المتوقعة: اجتياز 11 اختبارًا (وقت الإنشاء). يمكن فتح `web/index.html` ثم اختيار **عرض نموذج تجريبي**.

## تجربة فعلية لاحقًا على جهازك

- **لا تعدّل** `/system_data/priv/mms/app.db` ولا تعيد بناء قاعدة الألعاب لأجل المشروع.
- عندما يتوفر بناء PS4 موثّق للماسح، سيحتاج صلاحية قراءة `/system_data/priv/mms/app.db` و`/system_data/priv/appmeta`، ثم كتابة `inventory.json` تحت مجلد خاص بالتطبيق. قد يمنع عزل تطبيقات PS4 هذه القراءة حتى على جهاز معدل؛ لذلك يلزم اختبار على جهازك ونظام 14.00.
- أثناء التطوير فقط يمكن أخذ **نسخة** من قاعدة البيانات وبيانات SFO عبر FTP للاختبار على الكمبيوتر **دون رفع قاعدة بيانات النظام إلى GitHub أو هنا**؛ قد تتضمن تفاصيل خاصة بالجهاز والمستخدمين.
- راجع `native/BUILD_PS4_AR.md` لما يلزم قبل إنتاج ملف PKG. لا تحاول تغيير إصدار النظام أو GoldHEN.

## كيف تتكامل مع FPKGi؟

يقرأ `catalog/build_catalog.py` ملف الجرد وقائمة تحديثات **مصرّح بها ومجربة يدويًا**؛ ثم يولد `UPDATES.json` بصيغة متوافقة مع فهرس FPKGi. هذا **ليس فحصًا آليًا لتوفر تحديثات FPKG على الإنترنت**؛ العثور على ملفات التحديث، والتحقق من منشئها والتوافق القانوني والتقني، ما زال خطوة مستقلة.

الملف `catalog/approved_updates.csv` فارغ؛ لذلك `UPDATES.json` فارغ عن قصد. لا تستبدل به ملف `UPDATES.json` الحالي في GitHub بلا سبب.

## المصادر التقنية

- ItemzFlow: https://github.com/LightningMods/Itemzflow — راجع `itemzflow/include/utils.h` لمسار `app.db` و`itemzflow/source/sql.cpp` لاستعمال `tbl_appbrowse_*`, و`itemzflow/source/ls_dir.cpp` لمسارات `param.sfo`.
- OpenOrbis PS4 Toolchain: https://github.com/OpenOrbis/OpenOrbis-PS4-Toolchain
- FPKGi: https://github.com/ItsJokerZz/FPKGi

## ما ينقص ليصبح التطبيق النهائي

- بناء تطبيق PS4 وتوفير واجهة استخدام على السوني نفسه، وإتاحة قراءة قاعدة التطبيقات في بيئة GoldHEN.
- فحص تثبيت الألعاب بدقة على نظام 14.00 بدل الاعتماد على سجل app.db وملف SFO فقط.
- مصدر تحديثات متوافق مع FPKG، مع التحقق من المحتوى الذي يملكه المستخدم قانونيًا، ونظام تنزيل وتثبيت بموافقة واضحة.
- اختبار مباشر على السوني؛ ليس لدي وصول إلى جهازك من هذه الجلسة.
