# PS4 Auto Updater — شروط قبول الإصدار

**الحالة: MODIFY — غير جاهز للنشر.** هذه الوثيقة تخص فرع المراجعة التجريبي فقط، وليس الإصدار المنشور `v0.6.1`.

## ما تأكد فعليًا

- **Hardware / v0.6.1:** على PS4 يعمل GoldHEN FTP على المنفذ 2121. نجحت عمليات `LIST` و`RETR` لتسعة ملفات `param.sfo`. استُقبلت ترويسات `0x46535000`، لكن لم تُستخرج الحقول وأرجع الماسح `-33` لكل الألعاب التسع.
- **Hardware / v0.6.1:** فشل `sceSysmoduleLoadModuleInternal` لـ `AppInstUtil` مع `0x80020008`. هذا ليس إثباتًا لعدم وجود اللعبة.
- **تحليل ملف واقعي:** فهرس SFO المقروء خارجيًا أظهر Entry رقم 20 بطول `0x0A0D`؛ يتفق بقوة مع تحويل `LF` إلى `CRLF` خلال نقل FTP النصي، لكنه لا يثبت بعد إصلاح جميع الملفات.
- **CI:** اختبارات Host على بيانات اصطناعية، وبناء PS4 بنجاح عبر OpenOrbis. هذه ليست اختبارات تشغيل على PS4 firmware 14.00.
- **الإصدار المنشور:** يبقى `v0.6.1` غير نهائي، والمسار الجديد `v0.6.2` / `PKG 01.11` قيد التطوير ولم يُعتمد.

## تغييرات الفرع التجريبي

- استعادة LF المحوّل في **نسخة داخل الذاكرة فقط** إذا فشل التحليل الأصلي، ولا تُقبل النتيجة دون تحقق SFO وهوية CUSA وCATEGORY.
- تحقق كامل من Content ID، وتسجيل حالات نقص البيانات وتجاوز الحدود وفشل LIST الخارجي.
- حفظ الجرد بملف مؤقت ثم `rename` لتجنّب ملف JSON مقطوع، مع نسخ عناوين UTF-8 بطريقة صحيحة.
- واجهة PS4 أصلية باستخدام `VideoOut` و`Pad`، تعرض الحالة والتقدم الحقيقي وقائمة CUSA وتحذيرات البيانات غير المؤكدة، مع تصفح وخروج.
- تجربة تهيئة `sceAppInstUtilInitialize` من المكتبة المرتبطة مباشرةً كما يفعل ItemzFlow، دون اشتراط نجاح `sceSysmoduleLoadModuleInternal`؛ إذا فشلت، تبقى `install_state=UNKNOWN`.
- وضع تحديثات Retail/FPKG في مرحلة مراجعة بيانات فقط؛ تنزيل التحديث أو تثبيته معطّل افتراضيًا.

## اختبارات إيقاف النشر (Release blockers)

1. **Verified على الجهاز:** فتح واجهة PS4 14.00 والاستمرار فيها، التصفح والخروج باليد، التعامل مع فقدان FTP وعدم تعليق الشاشة أو تعطلها.
2. **Verified على الجهاز:** تقرير `/data/PS4AutoUpdater/diagnostic_v062.txt` وملف `inventory_v062.json` يجب أن يعرضا عنوانًا وإصدارًا وفئة متطابقة مع لعبة معروفة على الجهاز، دون أي خلط بين CUSA.
3. **Verified على الجهاز:** إثبات عمل استعلام `AppInstUtilAppExists` للقراءة فقط، أو بديل مكافئ موثوق. لا يكفي وجود مجلد SFO.
4. **PKG/FPKG:** فحص Title ID وContent ID والمنطقة وإصدار الأساس ونسخة التحديث ونوع PKG والحد الأدنى للـFirmware من مصدر حقيقي، لا من Metadata اصطناعية.
5. **المصادر والحقوق:** مصدر تحديثات قانوني ومصرّح به، والتحقق من السلامة والنزاهة والـSHA-256 الفعلي؛ metadata من XML عبر HTTP لا تثبت الأصالة أو توافق FPKG.
6. **التثبيت:** لا يُفعّل إلا بعد إثبات Install API وصلاحياته والحالة الفعلية والأخطاء والتعامل مع المساحة والإلغاء/الانقطاع على الجهاز؛ لا اختبار تثبيت خطر قبل تحقق مرحلة القراءة فقط.
7. **بناء وإصدار:** CI ناجح عند SHA الحالي، بدون تحذيرات Compile جديدة، وRelease artifact بسمات صحيحة وبصمة ثابتة، ويُمنع النشر التلقائي قبل إغلاق جميع نقاط العتاد والأمان.

## حدود الأمان

- لا تستخدم أبدًا `STOR` أو `DELE` أو تعديل `app.db` أو حفظ ألعاب المستخدم أو تحميل تحديثات دون تصريح.
- `scan_complete=false` يعني أن الجرد ليس شاملًا، وليس أن الألعاب مفقودة.
- أسماء المجلدات `CUSA` وحدها مرشحات؛ `metadata_verified` ليس إثبات تثبيت أو توافق تحديث.
- لا تُرفع ملفات بيانات ألعاب المستخدم الكاملة إلى مستودع GitHub العام.
- الاستفادة من مصادر ItemzFlow وOpenOrbis هي لفهم استدعاءات API والتصميم فقط؛ لا تنسخ أصولًا أو شيفرات تتطلب ترخيصًا غير متحقق منه.

## Decision log

- **ACCEPT:** Scanner read-only، التحقق الصارم من SFO، واجهة نتيجة الفحص، حدود الأخطاء ومؤشرات عدم اليقين.
- **MODIFY:** طريقة AppInstUtil، تعافٍ مشروط من تحويل FTP النصي، CI toolchain موثّق بصمته.
- **DEFER:** تنزيل التحديثات والتثبيت وواجهة اختيار الإصدارات إلى أن تثبت الحقوق والتوافق والتجربة على PS4.
- **REJECT:** إعلان التطبيق جاهزًا أو تأكيد تثبيت لعبة من CUSA أو اقتراح تحديث Retail رسمي كحل عام لتحديث FPKG.

## Build evidence ≠ Hardware evidence

اختبار `python3 -m unittest discover` يُثبت السلوك على بيانات وهمية. نجاح `make` وOpenOrbis يُثبت Compile/Link/PKG فقط. التشغيل الحقيقي والشاشة وقراءة العناوين والتوافق والأمان لا تُعد مكتملة دون اختبار موثّق على الجهاز.
